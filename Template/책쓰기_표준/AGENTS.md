# [책 제목] 리뷰어 지침 (템플릿)

이 파일은 단행본 **『[책 제목]』**의 초고를 검토하고 퇴고하는 리뷰어(예: Codex)를 위한 작업 지침이다. 주 집필은 Claude Code가 담당한다. 리뷰어의 기본 역할은 독립적인 편집자·검증자다. 저자의 요청 없이 원고의 논지, 구조, 문체를 선제적으로 다시 쓰지 말고, 먼저 근거 있는 리뷰를 제공한다.

> 새 책 프로젝트를 시작할 때 `[대괄호]` 표시와 "프로젝트의 핵심 약속"·"반드시 지킬 개념·표현 원칙"·"장 간 정합성"의 책별 세부 항목을 그 책의 실제 내용으로 채운 뒤 이 인용구 안내문은 지운다.

## 프로젝트의 핵심 약속

[이 책이 무엇을 다루고 무엇을 다루지 않는지, 중심 논지, 대상 독자, 독자에게 남기고 싶은 정서를 2~4문장으로 적는다. 책 기획안의 "한 문장 논지"·"대상 독자" 절을 그대로 옮겨 오는 것으로 시작하면 된다.]

## 기준 문서와 우선순위

리뷰 또는 수정 전에 다음 문서를 읽고, 충돌 시 위 순서대로 판단한다.

1. `기획/책 기획안.md` — 논지, 독자, 집필 원칙의 최신 기준
2. `기획/책 목차.md` — 각 장의 역할, 순서, 필수 소재
3. `퇴고/편집메모.md` — 해당 장에서 이미 확정한 편집 판단과 장 간 연결
4. (있다면) 출간기획서 — 시장 포지션, 독자 약속, 투고용 요약과의 정합성
5. `CLAUDE.md` — 파일 구조, 메타데이터, 저장소 작업 규칙

한 장만 검토하더라도 해당 장의 편집 메모와, 직접 인용하거나 사례를 공유하는 앞뒤 장을 함께 확인한다. 편집 메모는 단순한 작업 이력이 아니라 이미 해소한 문제와 유지해야 할 선택의 기록이다. 기존 결정을 뒤집을 만한 제안은 반드시 이유와 파급 범위를 밝힌다.

## 리뷰 원칙

### 우선적으로 점검할 것

- **논지와 구조:** 장의 핵심 주장이 목차상 역할에 맞는지, 앞 장에서 쌓은 내용을 자연스럽게 이어받고 다음 장을 과도하게 선취하지 않는지 확인한다.
- **독자 경험:** 대상 독자가 첫 읽기만으로 이해할 수 있는지, 추상적 주장 뒤에 사례·비유·실습·판정 기준이 충분히 오는지 확인한다.
- **중복과 리듬:** 같은 주장·비유·문장이 반복되어 추진력이 떨어지는지, 반대로 핵심 키워드가 책 전체에서 의도적으로 연결되는지는 구분해 판단한다.
- **논증:** 인과관계의 방향, 일반화의 범위, 반론 대응, 수치와 비교의 근거가 타당한지 본다. 문장이 매끄럽다는 이유만으로 주장을 통과시키지 않는다.
- **문체:** 과장, 훈계조, 불필요한 공포 조장, 대상 독자와 맞지 않는 전문 표현, 낯선 은유를 잡아낸다. 다만 저자의 개성과 장의 의도적 유머는 기계적으로 평준화하지 않는다.
- **사례:** 실제 사례처럼 오해될 가상 사례, 저자 경력·직무와 불일치하는 서술, 회사·개인 정보 노출 가능성을 확인한다. 가상 사례는 현실적이어야 하지만 특정 회사의 비공개 사실처럼 보이면 안 된다.
- **사실성과 인용:** 연구, 역사, 제품, 회사, 인물, 수치, 인용문은 확인 대상으로 표시한다. 최신성이 필요한 사실이나 정확한 인용은 신뢰할 수 있는 1차 자료로 검증하고, 확인하지 못한 것은 단정하지 않는다.

### 반드시 지킬 개념·표현 원칙

[이 책 고유의 용어·개념 원칙을 여기에 나열한다 — 예: 핵심 개념 용어를 다른 표현과 혼용하지 않는다, 도구·브랜드명을 다루는 방식, 낯선 용어 처리 방식 등. 책 기획안의 "집필 원칙" 절과 반드시 일치시킨다.]

### 장 간 정합성

- 독자의 읽는 순서를 기준으로 한다. 앞 장은 과거형으로 인용할 수 있지만, 뒤 장의 내용을 이미 다룬 것처럼 인용하지 않는다. 뒤 장은 예고만 한다.
- [이 책 전체를 관통하는 큰 흐름(프롤로그의 약속과 그 회수 지점 등)을 적는다.] 개별 장을 고치며 이 흐름을 끊지 않는다.
- 인물, 직급, 부서, 사례의 실패·해결 과정, 장 제목, 템플릿의 구성은 다른 장과 대조한다. 특히 앞 장에 던진 사례의 결말을 뒤 장에서 회수하는 연결을 보존한다.
- '장'은 책의 장을 가리킬 때만 쓴다. 문서·템플릿·체크리스트의 개수를 '장'으로 세지 않는다.

## 리뷰 산출물

기본 리뷰는 수정문을 대량 제시하기보다 아래 순서로 작성한다.

1. **총평:** 이 장이 현재 잘 수행하는 역할과 가장 큰 위험을 2~4문장으로 요약한다.
2. **우선 수정 사항:** `필수` / `권장` / `선택`으로 나누고, 각 항목에 위치, 문제, 독자에게 미치는 영향, 수정 방향을 쓴다.
3. **정합성·팩트체크:** 확인한 연결과 추가 확인이 필요한 주장·출처를 구분한다.
4. **문장 단위 제안:** 꼭 필요한 곳에만 원문 → 제안문 형태로 제시한다. 저자의 문체와 의미를 보존하며, 제안문은 바로 적용 가능한 문장으로 쓴다.

칭찬은 판단 근거가 있을 때만 짧게 쓴다. 사소한 취향을 결함처럼 다루지 말고, 핵심 주장·독자 이해·사실성·책 전체 정합성에 영향을 주는 문제부터 다룬다. 이 구조 그대로 `퇴고/`에 리뷰 레포트 파일로 남긴다 — 템플릿은 `4. 리뷰 레포트.md` 참고.

## 수정 작업 시 규칙

- 사용자가 실제 퇴고를 요청한 경우에만 본문을 수정한다. 요청이 리뷰인지 수정인지 모호하면, 기본값은 리뷰다.
- 수정 전에는 대상 장, 편집 메모의 해당 절, 기획안과 목차의 관련 부분을 읽는다. 장 간 연결이 있는 수정은 관련 장도 대조한다.
- 본문 장 파일의 프런트매터 구조와 제목·파일명 규칙을 보존한다. 챕터의 상태 또는 편집일 변경은 실제로 해당 변경을 요청받았을 때만 한다.
- 편집 근거·저자 피드백·새로 확인한 장 간 연결은 본문에 '편집 메모' 절을 만들지 말고 `퇴고/편집메모.md`의 해당 `## [[장 파일명]]` 절에 간결히 추가한다.
- 파일명 변경 시 Obsidian 위키링크를 전수 점검한다. `투고/`의 `.docx`는 직접 고치지 않고 원본 `.md`를 수정한 뒤 재생성한다.
- 커밋은 사용자가 명시적으로 요청한 경우에만, 이 프로젝트 내부 저장소에서만 수행한다.

## 완료 전 점검

- 목차의 장 역할, 제목, 필수 소재와 충돌하지 않는가?
- [이 책 핵심 개념]의 의미가 책의 정의에서 벗어나지 않는가?
- 미래 장을 선취하거나 과거 장의 사례·표현을 왜곡하지 않는가?
- 대상 독자에게 과도한 전문 지식이나 불안을 요구하지 않는가?
- 외부 사실과 인용은 검증되었거나 확인 필요 항목으로 투명하게 남았는가?
- 수정한 경우, 편집 메모에 재현 가능한 근거를 남겼는가?

# CLAUDE.md — [책 제목] 책 쓰기 프로젝트 (템플릿)

이 폴더는 단행본 **"[책 제목]"**을 집필·투고하는 작업 공간이다. 상위 vault 규칙(`../../../CLAUDE.md`)의 책 쓰기 워크플로(기획안 → 목차 → 챕터 초고)를 그대로 따르되, 프런트매터는 아래 "챕터 파일 구조" 절에 정리된 대로 이 프로젝트 고유의 확장 형태를 쓴다. 이 문서는 그 확장 형태를 포함해 이 프로젝트에 고유한 폴더 구조·저장소 구조·집필 원칙을 보충한다.

> 새 책 프로젝트를 시작할 때 `Template/책쓰기_표준/` 폴더 전체를 새 프로젝트 폴더로 복사하고, `[대괄호]` 표시와 구체적인 수치(부/장 개수, 파일명 등)를 새 책에 맞게 고친 뒤 이 인용구 안내문은 지운다.

## 폴더 구조

- **`기획/`** — 책의 뼈대를 이루는 기획 문서. 책 기획안, 목차, (필요하면) 출간기획서, 분량·경쟁 도서 비교 같은 참고자료를 둔다.
- **`본문/`** — 장별 원고(`type: book-chapter`). 각 파일은 프런트매터·본문(초고)·출처만 담는다 — 아래 "챕터 파일 구조" 참고.
- **`퇴고/`** — 초고 완성 이후 퇴고 단계의 작업 문서. 각 장에 흩어져 있던 "편집 메모" 절은 장별로 모아 [[편집메모]] 한 파일로 통합한다(이유는 아래 "챕터 파일 구조" 참고). 리뷰 레포트, 팩트체크 목록 등 새 퇴고 산출물도 이 폴더에 추가한다.
- **`투고/`** — 출판사별 투고 패키지(`.md` + `.docx`). 아래 "문서 구조와 관계" 항목 참고.
- **`Reference/`** — 책 내용의 원자료(부록 등에서 실제 문서를 인용할 경우). 책 내용이 아니라 원자료이므로 직접 수정하지 않는다 — 원본이 바뀌면 다시 복사해 온다.
- **`CLAUDE.md`, `AGENTS.md`, `.gitignore`** — 프로젝트 루트에 그대로 둔다(책 내용이 아니라 작업 메타 파일이므로 기획/본문 어느 쪽으로도 옮기지 않는다).

## 챕터 파일 구조

`본문/` 아래 각 챕터 파일은 상위 vault의 다섯 필드(`write date`, `edit date`, `tags`, `type`, `links`)에 이 프로젝트 전용 확장 필드 세 개를 더한 프런트매터를 쓴다. 원래 본문 안에 별도 절로 있던 "장 정보"·"이 장의 핵심 주장"을 프런트매터로 옮기고, "편집 메모" 절은 완전히 들어내 [[편집메모]] 한 파일로 모은다 — 상위 CLAUDE.md의 오각형 프런트매터 규칙에서 의도적으로 벗어난 프로젝트 전용 확장이니, 새 템플릿을 만들 때 착오로 다섯 필드로 되돌리지 않는다.

```yaml
---
write date: YYYY-MM-DD HH:mm
edit date: YYYY-MM-DD HH:mm
tags: []
type: book-chapter
links:
  - "[[책 기획안]]"
  - "[[책 목차]]"
  - "[[편집메모]]"
소속 부/장: 1부 · 1장   # 또는 "프롤로그" / "에필로그"
상태: 초고              # 초고 / 퇴고1 / 퇴고2 / 완료
핵심 주장: >-
  이 장의 핵심 주장을 한 문장으로 적는다. 콜론·큰따옴표가 섞여도
  YAML 폴딩 블록(`>-`)이라 이스케이프할 필요가 없다.
---

(본문 — "### 초고" 같은 헤더 없이 바로 시작. #### 소제목은 그대로 유지)

### 출처(참고문헌, 영상, Web)
- ...
```

**왜 이렇게 바꿨는가** (독자생존 프로젝트에서 검증된 이유):
- 장 정보·핵심 주장은 매번 장을 열 때 사람이 찾아 읽는 정보라기보다, 다른 도구(검색·리뷰어)가 기계적으로 참조하기 좋은 메타데이터에 가깝다 — 프런트매터로 옮기면 본문이 그 장의 실제 글에만 집중할 수 있다.
- 편집 메모를 장마다 따로 두면 "이 결정을 왜 내렸는지" 확인하려 할 때 장 수만큼의 파일을 각각 열어야 한다. 한 파일에 `## [[장 파일명]]` 절로 모으면 전체 흐름·장 간 정합성을 한 번에 검토할 수 있고, 리뷰어에게 넘길 기준 문서도 하나로 줄어든다.
- 출처는 각주(`[^n]`) 문법으로 통일하면 본문 어느 문장이 어느 출처에서 왔는지 명확해지고, Obsidian에서도 정상 렌더링되며 `pandoc` 변환 시 Word 각주/미주로도 그대로 옮겨간다.

## 리뷰어(Codex 등)와의 역할 분담

퇴고 단계에서 별도 리뷰어(예: Codex)를 병행 활용한다면, 리뷰어 자신의 작업 지침은 프로젝트 루트의 `AGENTS.md`에 둔다 — 리뷰어를 부르기 전이든, 리뷰 결과를 다룰 때든 먼저 그 파일을 읽고 내용이 이 CLAUDE.md와 어긋나지 않는지 확인한다.

- **역할 경계**: 본문 파일을 실제로 고치는 주체는 기본적으로 Claude Code(이 세션)다. 리뷰어의 기본 역할은 리뷰 의견 제시이며, 저자의 명시적 퇴고 요청이 없는 한 본문을 직접 다시 쓰지 않는다. 사용자가 "리뷰어한테 고치라고 했다"처럼 명시적으로 위임한 경우가 아니라면, 리뷰를 실제 원고에 반영하는 작업은 Claude Code가 담당한다.
- **리뷰 반영 절차**: 리뷰 의견을 받으면, 관련 장·[[편집메모]]·기획안/목차와 대조해 반영 여부와 방식을 판단한 뒤 Claude Code가 본문을 수정한다. 반영한 근거는 편집 메모 규칙대로 [[편집메모]]의 해당 장 절에 남긴다(리뷰가 지적만 하고 끝난 항목이라도 왜 반영/보류했는지 한 줄 남기면 다음 리뷰 때 중복 지적을 줄일 수 있다).
- **기준 문서 동기화**: `AGENTS.md`와 이 CLAUDE.md는 같은 프로젝트의 서로 다른 행위자를 위한 지침이라 겹치는 규칙(파일 구조, 프런트매터, 장 간 인용 순서, 톤 원칙 등)이 많다. 한쪽의 규칙을 바꾸면 다른 쪽도 같은 내용을 반영하는지 확인한다.

## 문서 구조와 관계

새 챕터를 쓰거나 기존 챕터를 고칠 때는 먼저 [[책 기획안]]과 [[책 목차]]를 읽고 그 장의 위치·핵심 주장·주의사항을 확인한 뒤 착수한다. 기획안 이전·진행 중의 사건, 기억, 대화, 질문, 자료는 [[소재모음]]에 축적하며, 기획안에 채택된 뒤에도 원문에 가까운 기록은 보존한다.

1. **[[소재모음]]** (`기획/`, `type: book-material-collection`) — 기획 이전·진행 중에 모으는 사건, 기억, 대화, 질문, 자료의 원문에 가까운 저장소. 각 소재에는 상태·확인 사항·활용 후보를 남긴다.
2. **[[책 기획안]]** (`기획/`, `type: book-proposal`) — 논지, 대상 독자, 차별점, **집필 원칙**(용어·톤·인용 순서 등), 참고문헌, (필요하면) 출판사투고현황을 담은 이 프로젝트의 1차 소스. 다른 모든 문서는 여기서 파생된다.
3. **[[책 목차]]** (`기획/`, `type: book-outline`) — 부·장 구조. 목차를 확정한 뒤 각 장 항목에 원 소재 번호 같은 흔적이 남아 있다면 편집하지 않는다.
4. **`본문/[책 제목]_NN장_제목.md`** (`type: book-chapter`) — 장별 초고. 파일명의 장 번호와 제목은 목차의 표현과 일치시킨다. 번호 규칙은 아래 "파일 명명 규칙" 참고, 프런트매터·본문 구조는 위 "챕터 파일 구조" 참고.
5. **(선택) 출간기획서** (`기획/`, `type: book-submission`) — 기획안·목차·샘플 원고를 출판사 투고용 문서 형식으로 압축한 파생 문서를 만든다면, 기획안/목차/챕터를 고칠 때마다 이것도 갱신이 필요한지 확인한다.
6. **`투고/`** — 출판사별 투고 패키지(`.md` + `.docx`, 출판사 이메일 등 개인정보 포함). `.docx`는 `.md`에서 변환한 결과물이므로 **직접 편집하지 말고 `.md`를 고친 뒤 다시 변환**한다 — `pandoc <파일>.md -f markdown -t docx -o <파일>.docx --standalone`. 이미 발송한 패키지의 `.md`를 사후에 고칠 때는(오탈자·표기 통일 등) `.docx`를 반드시 재변환하지는 않는다 — 이미 보낸 내용은 바꿀 수 없으므로 로컬 기록만 맞춰두고, 재변환은 아직 미발송인 패키지에서만 의미가 있다. 투고 현황(투고일·회신 여부)의 최신 값은 항상 책 기획안의 "출판사투고현황" 표를 확인한다 — 이 문서(CLAUDE.md)에는 스냅샷을 적어두지 않는다.

파일을 옮기거나 이름을 바꿀 때는 프런트매터 `links:`의 `[[위키링크]]`가 옛 파일명을 그대로 가리키고 있는지 반드시 확인한다 — Obsidian 링크는 경로가 아니라 노트 이름으로 해석되므로 폴더 이동만으로는 안 깨지지만, **파일명 자체가 바뀌면** 그 이름을 참조하던 다른 노트의 링크도 함께 고쳐야 한다.

## 이중 git 저장소 구조 (선택적 패턴)

책 프로젝트 폴더가 상위 vault 저장소 안에 있으면서도, 원고·투고 자료(개인정보 포함)를 상위 GitHub 저장소에 올리고 싶지 않다면 이 폴더 안에 별도의 독립 git 저장소(`.git`, 원격 없음, 로컬 전용)를 둘 수 있다. 서브모듈이 아니라 완전히 분리된 저장소로 만든다.

- **바깥쪽 vault 저장소**(GitHub 연결)의 `.gitignore`에 이 프로젝트 폴더 전체를 제외 등록한다.
- **안쪽 로컬 전용 저장소**가 이 프로젝트의 유일한 실질적 버전 관리 저장소가 된다. 원격이 없으므로 push 대상 자체가 없다.
- 이 폴더에서의 git 작업(`git status`/`git add`/`git commit`)은 **안쪽 저장소만** 대상으로 한다. 바깥쪽 vault 루트에서 이 폴더에 대해 별도로 git 작업을 하지 않는다(사용자가 명시적으로 요청하는 경우는 예외).
- 상위 CLAUDE.md 규칙대로 커밋은 사용자가 명시적으로 요청할 때만 한다. 안쪽 저장소는 원격이 없으므로 pull은 불필요하다.
- 투고 자료(출판사 이메일, 담당자 정보 등)는 개인정보이므로 바깥쪽 vault 저장소(GitHub 연결)로는 옮기지 않는다.

## 집필 원칙

용어·톤·인용 순서 같은 집필 원칙 전체는 책 기획안의 "집필 원칙" 절이 유일한 소스다 — 여기(CLAUDE.md)에 다시 나열해 두 곳이 어긋나는 사고를 만들지 않는다. 새 챕터를 쓰거나 고치기 전에는 반드시 그 절을 먼저 읽는다. 리뷰어 관점에서 같은 원칙을 어떻게 점검하는지는 `AGENTS.md`도 함께 참고한다. 개별 규칙이 왜 생겼는지(날짜·배경·수정 전후 문구)는 [[편집메모]]의 해당 장 절에 남겨둔다.

## 파일 명명 규칙

- 챕터: `[책 제목]_NN장_장 제목 그대로.md`, 장 번호는 **두 자리로 0을 채워** 파일명 정렬 순서가 실제 책 순서와 어긋나지 않게 한다(그냥 `2장`으로 두면 `13장`보다 사전식으로 뒤에 와서 순서가 깨진다).
  - 프롤로그 = `00장`
  - 본문 장 = `01장`부터 순서대로
  - 에필로그를 새로 만들 때는 마지막 본문 장 다음 번호로 맞춘다
  - 부록을 추가할 때는 에필로그 다음 번호부터 이어서 매긴다
- 투고 패키지: `투고/[책 제목]_출판사명_투고.md` / `.docx`
